# 通用策划案格式与 Penpot 制图标准 v1.6

状态：已采用  
通用模版参考：`B-庇护所.docx`  
简单模版：`Z-在线奖励.docx`  
简化评审案参考：`Y-英雄升级.docx`（2026-08-11 制作人批准；只学习结构、密度与图旁说明方法，不复制项目规则、数值、截图或残留内容）  
UE 结构参考：`庇护所ue流程图.vsdx`  
适用范围：功能策划案、系统策划案、活动策划案、UI/UE 说明、玩法子系统说明

## 0. 全局 Skill 与模板

所有项目的正式功能策划案默认调用个人 Skill：

- `$game-feature-design-docs`

根据复杂度只选择一份 Word 模板：

- **通用功能**：`game-feature-design-docs/assets/general-feature-design-template.docx`；模板库入口 `$artifact-template-game-feature-design-general`。
- **简单功能**：`game-feature-design-docs/assets/simple-feature-design-template.docx`；模板库入口 `$artifact-template-game-feature-design-simple`。

不得直接修改 Skill 内的母版。复制到项目策划目录后填写，并保留 DOCX、Penpot 可编辑源、对象级回读信息及 PNG 导出版本。

### Word-only 文档交付

- 所有正式、面向用户或用于项目评审的文档统一只交付可编辑 Word `.docx`，包括策划案、系统说明、活动方案、UI/UE 说明、研究总结、计划、报告、评审记录与验收说明。
- 不生成、不交付、不归档新的 PDF 文档或 PDF 评审版；历史 PDF 只可作为输入证据读取，不得复制、重导或放入新的交付包。
- DOCX 的排版质检使用逐页 PNG。若渲染工具内部必须短暂经过 PDF，该文件只能位于临时目录，质检结束即清理，不能进入项目目录、输出目录、版本库或交付清单。
- Penpot、流程图和页面说明图的评审导出统一使用 PNG，不生成 PDF 图。
- Markdown、CSV、JSON、YAML、源码和数据库等仅保留其工程、配置、机器读取或版本管理职责，不得代替正式 Word 文档。

### 默认可编辑设计工具

- 新项目与实质改版的 UI/UX、UE、系统流程、状态图和风格帧统一默认使用 Penpot。
- 正式策划案附 `Penpot UE & UI/UX Artifact Register`，记录 `penpot_url`、`workspace_id`、`project_id`、`file_id`、`page_or_board`、`object_refs`、`source_version`、`owner`、`review_state`、`coverage` 和 `local_source_backup`。
- 必须验证已认证的编辑权限、保存后重开或对象级回读，并核对 PNG 导出与可编辑源一致。
- 浏览器已打开、SVG/PNG、Mermaid、本地导入源或导入尝试都不能单独通过可编辑源门禁。
- 已验收的历史 Figma/FigJam 产物继续有效，不因默认工具变化而失效。只有制作人在项目 Profile 与受影响正式来源中明确批准时，新工作才可使用其他可编辑工具。

## 1. 核心结论

以后先判断**文档阶段**，再判断**功能复杂度**：

- **简化评审案（`REVIEW_ONLY`）**：用于方向评审、原型前对齐或快速解释体验、规则、UE、配置形态与玩家可见页面。它不是实现合同，不授权程序直接开工，也不能声称已经覆盖完整 QA。
- **最终实现案（`IMPLEMENTATION_CONTRACT`）**：作为策划、程序、数值、UI/美术、音频和 QA 的正式实现与验收来源。
- **低复杂度（`NARROW`）**：一条主循环、少量紧密相关页面/状态、少量配置、依赖与边界可以短句枚举。
- **实质复杂度（`MATERIAL`）**：跨系统、多页面、多状态、配置密集、成长/经济/战斗影响明显，或存在批量、存档、中断、重连、并发、刷新、补偿等歧义风险。

简化评审案只保留当前决策所需信息；最终实现案必须补齐实现和验收责任面。复杂功能可以先写简化评审案，但必须写明 `NOT AUTHORIZED FOR IMPLEMENTATION`、缺失的最终章节、负责人和升级条件，并在实现开始前迁移到通用最终模板。不得把同一份不完整评审稿改个状态就冒充最终实现案。

## 2. 两种模版的共同骨架

### 1. 版本管理

必须放在第一页，不另做装饰性封面。

包含：

- 版本控制：文件状态、文档编号、作者、制作策划、制作程序、制作美术、当前版本、创建日期、完成日期、备注。
- 版本历史：版本、编写人、审核人、批准人、日期、更新内容。
- 开发计划：策划、美术、程序等责任方的开始时间与预计完成天数。

### 2. 目录

使用 Word 真实标题样式和自动目录，不手工输入页码。目录应覆盖到三级标题，并在交付前更新。

### 3. 文档内容

固定顺序：

1. 术语缩写与修订标记
2. 设计目的
3. 功能概述
4. 系统框架（通用版必需，简单版按需）
5. UE 总流程图（简单版、通用版均必需）
6. 参考视频（存在动态参考时）
7. 配置表调整
8. 系统逻辑
9. UI 界面及子玩法

### 4. 相关需求

至少检查：

- 美术资源需求
- 音乐音效需求
- 功能打点需求

没有需求时写“无”，不能直接删掉标题，让下游误以为漏写。

### 5. 关联拓展

说明与本功能有关但不在当前版本实现的系统、版本扩展、复用入口和已知耦合。当前版本不做的内容必须明确标为非本期范围。

## 3. 文档阶段与模板选择

| 文档阶段 | 低复杂度 `NARROW` | 实质复杂度 `MATERIAL` |
|---|---|---|
| `REVIEW_ONLY` | 使用简单模板 | 允许使用明确标记的简化评审案；必须列出缺失的最终责任面与升级条件 |
| `IMPLEMENTATION_CONTRACT` | 只有全部简单最终条件通过时才用简单模板 | 必须使用通用最终模板 |

简单模板能够作为最终实现案的前提是以下条件全部成立：

- 一条清晰主循环，主页面及紧密关联状态数量少；
- 一张表或少量直接映射字段；
- 依赖、边界、失败与返回均可短句枚举；
- 没有重大跨系统、经济、概率、存档、批量、重连或并发歧义；
- 程序与 QA 短读后只有一种合理解释。

下列任一情况出现时，最终实现案必须使用通用模板：

- 功能会改变核心循环、成长、经济或战斗结果。
- 存在多个入口、返回路径、弹窗、子玩法或非平凡页面跳转。
- 存在锁定、解锁、可用、资源不足、已完成、已领取、售罄、过期、失败等多状态。
- 需要跨多个配置表、存档、服务器状态、运行时服务或引用校验链。
- 存在批量、重置、返还、刷新、中断、重连、跨日、并发、回滚或补偿规则。
- 程序或 QA 若只读文字，仍可能对状态机、数据权威、刷新时机或边界处理产生两种解释。

## 3.1 简化评审案标准流程

简化不是把最终模板随意删短，而是为当前评审只保留能形成决定的信息。固定按以下顺序执行：

1. **只读需求回执**：确认功能目标、玩家可见结果、范围、非目标、负责人、依赖、现有基线、输出路径、配置来源和评审目的；记录 `document_class=REVIEW_ONLY` 与 `implementation_authority=false`。
2. **体验预期**：用 1～3 条说明玩家为什么需要该功能、玩家应该形成什么预期。
3. **核心聚焦**：用 3～5 条玩家可感知规则说明主要行为，再用一句话规则锁定系统。正文优先回答“玩家怎么看、何时变化、如何反馈”。
4. **UE 总流程**：列出关键页面、弹窗、HUD 和必要状态；用页面 UE Frame 组成可编辑总图，标明入口、主要操作、反馈、分支、返回和重进。不得用纯页面名称框、纯文字箭头或无序缩略图墙替代。
5. **配置形态**：只列直接驱动页面和核心规则的配置表与字段，使用准确表名、字段名、类型和简短语义；不在正文重复整张表。
6. **核心逻辑**：优先用一张小流程图和短句说明对象分类、解锁、操作、结果与关键阻断，不为尚未进入最终实现阶段的内容扩写大状态矩阵。
7. **图旁页面说明**：以真实截图、已批准线框或低保真页面图为主体，在图旁说明入口、默认位置、主要按钮、显示条件、状态差异、数据来源、反馈和去向。截图承载语境，正文不重复描述可直接看见的布局。
8. **边界与未知**：列出当前评审必须决定的边界；尚未要求展开的实现边界写入“最终实现案待补”，不得写“暂无”来掩盖已知风险。
9. **相关需求与系统**：简要记录音频、打点、技能、属性、存档或其他依赖；删除与本功能无关的模板残留。
10. **升级清单**：列出迁移到最终实现案前必须补齐的系统框架、状态/数据权威、完整配置校验、持久化/中断规则、资源规格、QA 与验收内容，并写负责人和关闭条件。

简化评审案必须在首页或显著位置写明 `REVIEW_ONLY / NOT AUTHORIZED FOR IMPLEMENTATION`。其批准只代表方向可继续，不代表实现、运行时行为或 QA 完成。

## 3.2 简单最终实现案标准流程

低复杂度功能只有在第 3 节的简单最终条件全部成立时，才可使用简单模板作为 `IMPLEMENTATION_CONTRACT`。此时必须保留版本管理、目录、设计目标、功能概述、UE、准确配置来源、核心逻辑、边界与状态、UI、资源/音频/打点、关联系统、QA、待确认项和升级条件；不得因为页数少而删除责任面。

通用执行顺序：

1. 完成只读需求回执与现有运行/UI 基线。
2. 写一句玩家记忆点与 3～5 条可感知规则。
3. 完成页面 UE Frame 与 UE 总流程图。
4. 完成低保真游戏内位置、信息层级和关键状态说明。
5. 写准确配置来源、硬性数据/时间契约、边界、异常配置和 QA。
6. 完成主策与制作人文档级审核；文档审核不代替运行时验收。
7. 交付 DOCX、Penpot 可编辑源及登记表、PNG、配置来源和审核记录；不可验证的门禁保持 `Pending`。

实施前门禁：

- 主策与制作人文档级审核通过；
- Word、Penpot 与配置来源内容一致；
- UI/UE 简图能直接看出游戏内位置和关键状态；
- 所有未决项均写 `Pending`、负责人和关闭条件；
- 若简化评审案进入实现准备，或简单功能新增跨系统、多页面、多状态、配置密集、存档/批量或中断/重连风险，必须在实现继续前迁移到通用最终模板。

策划完成与功能完成必须分开记录。策划案、静态图或文件存在只证明“设计包可评审”；功能只有在真实运行时行为、边界用例和回归证据通过后才能关闭。

## 4. 各章节写作要求

### 4.1 术语缩写与修订标记

沿用模版的语义色：

- **红色**：重要规则、强约束、当前版本必须注意的行为。
- **蓝色**：本版本新增或修改内容。
- **绿色**：数值、配置表、字段、数据源和可调参数。
- **灰色**：策划备注、解释性说明、非正式规则。
- **删除线**：已删除或被替代的旧规则。

颜色不能代替文字说明。版本历史必须说明本次新增、修改、删除了什么。

### 4.2 设计目的

写玩家体验和产品目的，不写实现手段。推荐分成：

- 主要目标：必须解决的问题和玩家可感知结果。
- 次要目标：优化项、差异化或后续价值。
- 非目标：本版本明确不处理的内容。

### 4.3 功能概述

用 3-8 条短句说明完整主循环。读者应能在一分钟内理解：

- 入口是什么；
- 玩家做什么；
- 系统如何反馈；
- 成功/失败或结束条件是什么；
- 奖励、消耗或状态变化是什么。

### 4.4 系统框架

通用版必须提供一张 Penpot 系统框架图，说明：

- 设计目的与预期；
- 系统包含的机制；
- 触发与结束条件；
- 选择、奖励、消耗与刷新；
- 边界及关联系统。

框架图用于快速理解系统，不替代后续可执行规则。

### 4.5 UE 总流程图

**UE 总流程图**是把本功能涉及的各个关键页面 UE 图放在同一张可编辑画布中，展示玩家从入口进入后，页面如何衔接、功能如何运转、状态如何变化，以及怎样结束、返回或再次进入。它不是纯页面清单、纯状态机、程序事件图，也不是把截图无序缩小后拼成一面缩略图墙。

制作顺序固定为：

1. 建立页面清单，为每个页面、弹窗、HUD、结果页和必要状态分配唯一页面 ID。
2. 为清单中的每个页面制作 UE Frame，至少表现信息层级、主要可操作元素和关键反馈；同一页面的多个状态放入同一页面状态组。
3. 把所有页面 UE Board 放入同一 Penpot 总流程画板。
4. 按真实游戏顺序连接入口、主循环、页面内操作、系统反馈、分支、结果、返回、重进和终止路径。
5. 在每条连线上写明玩家动作、系统事件或条件，不得只画无标签箭头。
6. 用页面清单和书面跳转表反查总图，保证没有漏页、孤立节点或无去向分支。

UE 总流程图必须由 Penpot 制作，并同时提供：

- 可编辑的 Penpot 链接、文件/页面/画板/对象引用与本地源备份；
- PNG 评审导出；
- 插入策划案的清晰版本；
- 书面跳转说明。

总图节点必须是对应页面的真实界面截图、已批准线框图或清晰 UE 占位 Frame，而不是只有页面名称的空框。每个连接必须说明玩家动作、系统事件或条件，例如“点击入口”“拖拽完成”“奖励到账”“倒计时结束”“购买成功”“返回上一级”。

必须覆盖：

- 进入条件和入口；
- 主路径；
- 返回、关闭、确认、取消；
- 弹窗及弹窗关闭后的去向；
- 成功、失败、重试；
- 空状态、资源不足、售罄/已领取；
- 中断、重开、重连、刷新和过期；
- 边界情况下最终落到哪个页面或状态。

若页面过多，可把复杂子流程拆为独立 Frame，但必须保留一张根级 UE 总流程图，标明子流程入口、出口和回到主流程的位置。策划案中的页面清单、逐页 UE 说明、书面跳转表和 UE 总流程图必须使用相同页面 ID、状态名和版本。

### 4.6 配置表调整

配置表说明使用固定四列：

| 名称 | 字段名 | 数据类型 | 备注 |
|---|---|---|---|

备注必须说明语义、单位、默认值、取值范围、通用规则和特殊行为。不得只写“见配置”。

数据源按项目正式管线填写：

- Godot 项目默认写到准确的 `config/csv/*.csv::column`；
- Resource 写 `ResourceName.field`；
- 存档写 `SaveData.field`；
- 运行时服务写 `Service.event/state`；
- 使用工作簿或数据库的项目写准确表名、页签、字段和主键。

用户已经修改过的配置表是数值和内容的来源，策划案不得用模版值覆盖。

### 4.7 系统逻辑

通用版先放“系统整体逻辑流程图”，再拆分每个机制。整体逻辑图优先使用三泳道：

1. 玩家操作
2. 表现
3. 系统逻辑

每个机制至少说明：

- 触发条件；
- 前置校验；
- 状态与计时；
- 数据读取；
- 随机、权重、保底或刷新规则；
- 资源发放与扣除；
- UI/音效/动画反馈；
- 退出、失败、中断和重进；
- 边界情况。

有判断时使用菱形节点；有倒计时时写明起点、暂停条件、最后提示和结束结果；有随机时写清样本池、是否放回、权重单位、保底和种子/复现要求。

### 4.8 UI 界面及子玩法

每个页面、弹窗、HUD、结算页和子玩法独立成节。固定使用以下顺序：

1. **界面入口（流程）**
2. **玩法机制**
3. **界面内容**
4. **交互反馈**
5. **显示条件和状态**
6. **数据来源**
7. **异常与边界**

效果图应编号标注。图上用序号框出标题、货币、列表、按钮、提示、进度、红点等信息元素，正文按相同序号解释：

- 元素表示什么；
- 什么条件下显示；
- 点击/长按/返回后的行为；
- 禁用、锁定、加载、空、错误等状态；
- 对应数据源；
- 谁负责更新；
- 刷新时机。

不要把一张很小的整页截图当成完整 UI 说明。关键组件、状态变化和文案应放大展示。

## 5. Penpot 制图标准

### 5.1 文件结构

推荐命名：

- 文件：`[项目] [功能ID] [功能名] UE vX.Y`
- 页面：`01_系统框架`、`02_UE流程`、`03_系统逻辑`、`04_页面说明`、`05_状态与边界`、`99_归档`

每个正式图都要有标题、版本、负责人、更新时间和对应策划案编号。

### 5.2 UE 总流程图

- 使用从左到右或从上到下的单一阅读方向。
- 节点使用各页面 UE Frame；先完成逐页 UE，再组合总流程。
- 总图必须能从页面构成直接看出玩法如何运转，不得退化为纯页面名称框或无序截图拼贴。
- 主路径使用最明显的连接线；异常、失败和返回路径使用次级颜色或虚线。
- 箭头必须有动作/事件标签。
- 入口、主页面、弹窗、结果页和返回点都要清楚。
- 同一个页面的多个状态放在一个状态组中，不散落在画布各处。
- 页面清单中的每个关键页面必须在总图出现；总图节点必须反向链接到逐页 UE 说明。
- 节点间保持足够间距，禁止交叉线遮住截图或文字。

### 5.3 系统逻辑图

- 默认使用“玩家操作 / 表现 / 系统逻辑”三泳道。
- 规则节点写行为，判断节点写问题，连线上写结果。
- 配置表/字段用绿色标注，但仍保留完整字段文字。
- 计时、刷新、奖励、扣除、保存、重进都要有明确节点。
- 复杂子流程可拆成独立 Frame，并从总图链接过去。

### 5.4 页面说明图

- 优先使用 Penpot 组件、Flex Layout 和 Grid Layout，避免无法维护的散乱截图拼贴。
- 在截图或线框上使用统一编号标注。
- 同一页面至少检查默认、禁用/锁定、加载、空、成功、失败和异常状态中适用的部分。
- 参考商业产品只能学习信息结构和交互原则，不复制角色、品牌、图标、独特布局或商业美术。

### 5.5 导出与归档

- 通过保存重开或对象级回读验证的 Penpot 可编辑文件是正式源。
- 评审导出只使用 PNG，文字必须可读。
- 文档中同时写明链接、版本和导出日期。
- Mermaid、ASCII 图或文字箭头仅可用于草稿，不作为最终策划图。

## 6. 文档版式

沿用两份模版的视觉系统：

- A4 竖版，四边约 15 mm 页边距。
- 正文宋体 10.5 pt；中文正文默认左对齐，禁止用两端/分散对齐配合手动换行。
- 一级标题：宋体 22 pt，加粗。
- 二级标题：黑体 16 pt，加粗。
- 三级标题：宋体 12 pt，加粗。
- 页眉不得使用侵入正文标题区的横线或边框；页脚右侧使用“当前页 / 总页数”。
- 版本与计划表使用浅灰表头；配置、资源和需求表使用浅蓝表头。
- 表格允许自动增高，不用固定行高截断文字。
- 图片紧跟对应标题和解释；复杂图单独占页或拆分，不缩成不可读缩略图。

正式 DOCX 必须逐页渲染检查：无文字裁切、无表格断裂、无图片模糊、无大面积无意义空白、目录与页码正确。

## 7. 交付包

正式策划案至少包含：

- 可编辑 DOCX；
- Penpot 可编辑链接、Artifact Register 与本地源备份；
- Penpot PNG 导出；
- 相关配置表或准确的数据源路径；
- 需要时的参考视频；
- 美术、音频、打点需求；
- 独立 QA/验收清单或任务验收回执。

通用版应将所有图、表、页面规则和机制规则统一到同一个内容模型中。Word、Penpot、配置表和实现任务之间不能出现互相冲突的字段、状态或版本。

## 8. 完成门槛

最终实现案只有同时满足以下条件才算可交付：

- 一分钟内能从设计目的、功能概述和框架图理解系统。
- 程序能找到状态、数据源、事件、刷新时机和边界处理。
- 数值策划能找到全部可调字段、单位、默认值和公式归属。
- UI/美术能找到每个页面、组件、状态、尺寸/格式与优先级。
- QA 能推导正常、边界、空、满、中断、失败和回归用例。
- Penpot 图可编辑、对象引用可回读，导出清晰，正文中的图与当前版本一致。
- UE 总流程图由页面清单中的各关键页面 UE Frame 组成，能读出完整运行过程；页面 ID、跳转、动作/事件、分支、返回和逐页说明互相一致。
- 所有未决定内容标记为“待确认”，并写责任人；不得把猜测写成已批准规则。
- 用户评审并修改后的 Word、Penpot 和配置表是最终来源，下游任务必须随之更新。

简化评审案的完成状态只能是“方向可评审/已评审”，不得沿用本节的“最终实现案可交付”结论。它必须保留升级清单，直到相应最终实现案完成并通过本节门槛。
